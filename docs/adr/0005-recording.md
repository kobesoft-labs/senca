# ADR-0005 録画の形式と索引

- 状態: 採用（2026-11-02）
- 関係: 仕様 5.3・8.4、REQ-002（重なる予約で入力とセグメントを共有）、REQ-006 R6-1、REQ-010 R10-7

## 決定

1. **セグメントは stream ごとに 1 回だけ作る。** stream タスクがライブ HLS 用に作ったセグメント（TS または fMP4 のバイト列、`Bytes`）を、そのまま録画にも使う。録画のために別に多重化しない（R10-7）。
2. **不変のファイル。** 誰かが録画しているときだけ `segments/{stream}/{run}/{name}` に書く（一時名 → fsync → rename）。書いたら変えない。`run` はノードの起動ごと・stream タスクごとの ID。
3. **録画ごとの索引は追記のみの JSON Lines。** `recordings/{id}/index.jsonl`。行の種類は `begin`・`init`・`segment`・`gap`・`end`（`senca-record::Entry`）。1 行ごとに fsync。
   - 書く順番: セグメントのファイル → 索引の行。索引にあるセグメントは常に完全。
   - 末尾の書きかけの行は回収で切り捨てる。途中の行が壊れていたら索引に触らない（消さない）。
4. **共有。** 同じ時間に複数の録画があれば、同じセグメントのファイルを各索引が参照する（容量は 1 本分）。録画の削除で、どの索引からも参照されなくなったセグメントだけを消す。
5. **境目はセグメント単位。** 録画の開始・停止はセグメントと同じキューで書き手に届く。開始は「今作っているセグメント」から、停止は「停止時刻を含むセグメント」まで。正確な開始・終了は索引の `not_before_ms`・`not_after_ms` に持ち、MP4 の書き出しで切り出す。
6. **ライブ優先。** 書き手へのキューは有界で、あふれたらセグメントを落とし、次のセグメントの前に `gap`（`queue_overflow`、落とした数）を記録する。ライブは止めない（仕様 5.3）。
7. **書き手はファイル I/O をブロックで行うので専用のスレッド**で動かす（tokio のワーカーを止めない）。

## 回収（起動時）

- `end` の無い索引は、末尾を切り詰めて `end`（`interrupted`）を足す。制御状態の録画も `interrupted` にする。
- 索引から参照されていないセグメントは `segments/.../orphans/` に移す（消さない）。
- `--verify-recordings` で各セグメントの SHA-256 を照合する。

## 仕様との違い

- 仕様 8.4 の `recording_id/epoch/track/segment` の階層ではなく、映像・音声を 1 本のセグメントに多重化する。プレイヤーとの互換と、ライブとの共有を優先した（台帳に記録）。
