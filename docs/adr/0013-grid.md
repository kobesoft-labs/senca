# ADR-0013 グリッドでの配置と縮退運転

- 状態: 採用（2026-11-03、利用者の指示「全てがグリッドで動き、マニュアルでのハードウェア割り当てもできるが、Docker Swarm のように、一部のハードウェアが停止した場合にも縮退して全体がちゃんと動く。コントロールノードで。通信もボトルネックになるので効率よく」）
- 関係: 仕様 8 章、REQ-005、REQ-010（R10-4・R10-9）、ADR-0009

## 用語

- **ノード**: senca-node の 1 プロセス。役割 `control`（Raft の投票者）と `media`（仕事を動かす）を持つ。1 台が両方でもよい。
- **資源**: ノードが報告する容量と使用量。`cpu_millis`・`memory_mb`・`net_mbps`（送受）・`gpu`（装置ごとの符号化・復号セッション数、メモリ）・`capture`（キャプチャ機器）・`labels`（`zone`・`rack` など）。
- **仕事（workload）**: グリッドで配置する単位。種類は `ingest`（stream の受信と HLS）・`room`（リアルタイムの部屋の一部）・`pipeline`（変換・合成）・`recording`・`transcode`・`capture`・`relay`・`media_pipeline`。仕事は**要求する資源**・**制約**・**優先度**・**縮退の段**を持つ。
- **割り当て（assignment）**: 仕事 → ノード（と装置）。合意ログに載せ、fencing token を持つ（ADR-0009）。

## 決定

1. **配置は制御ノード（Raft のリーダー）が行う。** リーダーだけが配置の係を動かし、決定を `Assign` コマンドとして合意ログに載せる。各ノードは自分に割り当てられた仕事だけを動かす（突き合わせの係）。
2. **ノードの健康**: 各ノードは 1 秒ごとに心拍（資源の使用量・装置の状態・仕事の状態）をリーダーへ送る。心拍は合意ログに載せない（量が多い）。リーダーは心拍の途絶（既定 5 秒）か、装置の故障の報告で `NodeDown`／`DeviceDown` を合意ログに載せる。
3. **配置の方針**（Swarm の考え方）:
   - 制約: `node`（手動でノードを指定）・`device`（手動で GPU などを指定）・`labels`（`zone=a` など）・`anti_affinity`（同じ仕事の複製を別のノードへ）。
   - 置き方: 既定は spread（余裕の多いノードへ）。`binpack` を選べる。データのある所を優先する（入力を受けているノードに変換・録画を置く。R10-9）。
   - 手動の割り当て（`pinned`）は、そのノード・装置が生きている限り動かさない。止まったら、`pin_policy` が `strict` なら止めたまま、`prefer` なら他へ移す。
4. **縮退**: 仕事は優先度（`critical`・`high`・`normal`・`low`）と縮退の段（例: 録画 > 配信の最高画質 > 中画質 > 低画質、字幕・翻訳・サムネイルは省ける）を持つ。資源が足りないとき、配置の係は
   1. 低い優先度の仕事の省ける部分（翻訳・サムネイル・高い画質の段）を外し、
   2. それでも足りなければ低い優先度の仕事を止め（追い出し）、
   3. 高い優先度の仕事を生きているノードへ割り当てる。
   縮退した状態は API とイベントで見える（`degraded` と理由）。資源が戻れば元に戻す。
5. **振り直しの安全**: 新しい割り当ては新しい fencing token を持つ。古いノードは自分の token が古いと分かった時点で止める（二重に動かさない）。外部への副作用（録画の確定・出力の公開）は token を検査する。
6. **通信の効率**（ADR-0014）: ノード間は 1 本の多重化した接続、購読の集約、優先度つきの送り、生のフレームを運ばない。

## 検証

- 配置の係は sans-io（決定的なシミュレーションで、ノードの停止・復帰、GPU の故障、手動の割り当て、資源の不足での縮退と回復を検査）。
- 3〜5 台の実プロセスで、ノード・装置を止めて仕事が移る・縮退する・戻ることを確かめる。

## 実装の状況（2026-11-03）

- 置く仕事: 入力（`ingest`・`capture`）、出力（`egress`）、パイプライン（`pipeline`）、部屋（`room`。メディアパイプラインの書き出しは部屋の仕事に含め、合成は別のパイプライン）。
  録画・変換・中継は、それぞれの stream・パイプラインの仕事の中で動く（別の仕事にしていない）。
- 決定は `ApplyDecisions` で合意ログに載せる（全部か何もしないか）。
- 心拍の使用量はまだ 0、装置の健康もまだ測っていない（いつも健康）。壊れた装置は運用者が手で止める（`POST /nodes/{id}/devices/{dev}/disable`。心拍では戻らない）。
- fencing: ノードは新しい token の割り当てを適用したときに古い仕事を止める。外への副作用の前の `is_current` の確かめはまだ入れていない
  （ネットワークが分かれた少数側のノードは、多数側が移した仕事を続けうる）。
- `placement.device` は GPU だけに合う（キャプチャ機器は入力の `url` の `device:` で決まる）。
- 部屋は `senca.io/webrtc=true` のノード（`--webrtc-udp` を開いたノード）にだけ置く。
