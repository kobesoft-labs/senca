# ADR-0009 分散の制御面

- 状態: 採用（2026-11-02）
- 関係: 仕様 8.1・8.2・AC-15・AC-16、REQ-005、REQ-010

## 決定

- 制御状態のすべての変更（`Command`）を自前の Raft（senca-raft）で複製する。投票者は 1〜7 台（`--cluster-config`）。
- ノードの中では `App::propose` が唯一の入口。単一ノードでは追記ログ（`control/log`）、分散では Raft のログ（`control/raft/`）に書く。
- 駆動役は専用のスレッドで、Ready を「永続化（fsync）→ 送信 → 適用」の順に処理する。永続化に失敗したらノードを止める（送信も適用もしない）。
- **提案はどのノードからでもできる。** リーダーでなければリーダーへ転送し、適用の結果を受け取る。リーダーが分からない・過半数がいない・5 秒以内に適用されないときは 503（retryable）。過半数を失った側は書き込めない（仕様 8.1）。
- **早めの 4xx**: 提案の前に手元の写しで試す。確定の結果は合意後の適用で決まる（同じコマンドは全ノードで同じ結果）。
- 1000 件ごとに制御状態の写し（スナップショット）を作り、古いログを捨てる。
- 初期化（再生 URL の鍵・最初の管理者トークン）は ID が最小のノードだけが行い、状態を見てから提案する（何度走っても同じ）。各ノードは自分を `PutNode` で登録する。
- ノード間の通信は mTLS（仕様 9.2）の上の枠（種類＋長さ）。クラスタの認証局（`tls_ca`）で発行したノードの証明書（SAN に `senca-cluster`、serverAuth・clientAuth）を双方が検証する。`tls_*` を書かなければ平文（閉じたネットワークでの試験用）。
- **ノードの相互認証（挑戦応答）**: Raft と中継の接続は、枠の前（TLS の中）で、クラスタの合言葉から HKDF-SHA256 で導いた鍵（用途ごとに別）による相互の挑戦応答を行う。つなぐ側が番号と乱数 `nc`、受ける側が番号・乱数 `ns`・`HMAC(K, "server" ‖ 用途 ‖ 番号 ‖ nc ‖ ns)` を返し、つなぐ側は相手が宛先の番号で MAC が合うことを確かめてから `HMAC(K, "client" ‖ …)` を送る。合言葉も固定の値も送らない（以前の版は合言葉の SHA-256 を毎回送っていたので、見られると送り直しで入れた）。長さは固定、全体で 5 秒。中継では、中継の握手で名乗った番号が挑戦応答で確かめた番号と同じかも確かめる。
- **秘密値の鍵はクラスタ共通**: 秘密値（仕様 9.3）はクラスタ共通のデータ鍵で封じる。データ鍵は合言葉から HKDF-SHA256 で導いた鍵で AES-256-GCM により包み、制御状態（`secret_data_key`）で複製する。`SetSecretDataKey` は最初に適用されたものだけが効く（決定的）。どのノードも、まだ無ければ自分の `control/secret-key` を包んで提案する。
  開くときはデータ鍵の次にノードの鍵も試し、ノードの鍵でしか開けない値（以前の版で封じたもの）は起動の初期化の後にデータ鍵で封じ直す（移行）。単一ノードは今までどおりノードの鍵で封じる。
  選ばなかった案: 合言葉から決定的にデータ鍵を導く（合言葉の入れ替えで全部の値を封じ直す必要があり、既存の値の移行もできない）、ノードの鍵をファイルで配る（運用で写し忘れる）。KMS は後で置き換えられる。

## メディアの所有権（仕様 8.2）

- 送り手がつながったノードは `ClaimStream` を提案する。適用で fencing token（`fencing_counter`）を払い出し、`owners[stream]` に（ノード、token）を記録する。
- 入力が終わり再接続の猶予が切れたら、所有者は `ReleaseStream`（token が今のものと同じときだけ外れる）を提案する。`NodeDown` の適用でも、そのノードの所有者の記録を外す。戻ったノードが送り手を受けたままなら所有権を取り直す。
- 他のノードは適用されたコマンドを見て、自分が持っていた stream の送り手を切る（`HubEvent` で購読者は終わりを知る）。古い所有者は二重に公開しない。
- 視聴（署名付きのライブ・録画）の要求が、データを持たないノードに来たら 307 で所有者（録画は録ったノード）の公開 URL へ案内する。仕事はデータのある所で行い、ノード間で生のフレームを運ばない（REQ-010 R10-9）。

## 仕様との違い・未了

- **読みはそのノードの状態から**（ReadIndex を通さない）。書きは線形化可能、読みは数 ms 遅れうる。強い読みが要る操作は M9 の続きで ReadIndex を通す。
- 視聴者の多い stream の中継の木（ノード間でメディアを中継して配る）は未了。今は所有者への案内（リダイレクト）。
- 録画はノードの手元のディスク。共有のオブジェクトストレージは未了。

## 検証

- senca-raft の決定的なシミュレーション（安全性の不変条件、6000 通り以上）。
- `tools/interop/cluster.sh`: 3 台で、どのノードからでも書ける、重複は 409、1 台を止めても書ける、戻ったノードが追いつく、過半数を失うと 503・`/readyz` も 503・読みはできる、回復で書ける、全ノードが収束する。所有者への案内、所有権の移動で古い送り手が切られる、新しい所有者の配信が見える、入力が終わると所有権を手放す。平文では合言葉を知らない相手が挑戦応答で拒まれる。`CLUSTER_TLS=1` で mTLS、別の認証局の証明書のノードは拒否。

## 実装の状況（2026-11-03）

- ノード間は mTLS（証明書が無いときは平文。閉じたネットワークだけ）。どちらでも合言葉による相互の挑戦応答で番号を確かめる。
- 秘密値はクラスタ共通のデータ鍵で封じる（合言葉で包んで複製。以前の版のノードごとの鍵からは自動で封じ直す）。合言葉の入れ替えはまだ無い（変えると包みを開けない）。
- 所有者でないノードの視聴者は、中継の写し（ADR-0014）から配る。所有者への 307 の案内は、中継が使えないときの予備。
- 入力が終わると所有権を手放す（`ReleaseStream`）。停止と見なしたノードの所有権は `NodeDown` で外す。
- 過半数との連絡: リーダーは過半数の投票者から最後に返事を受けた時刻、フォロワーはリーダーから最後に受けた時刻を持つ。4 秒を超えて古いノードは `/readyz` を 503 にし、グリッドの仕事を止める（ADR-0013）。
- 中継の待ち受けの既定（Raft + 1）が他のノードの Raft・中継の宛先とぶつかる設定は、起動の検査で止める。
