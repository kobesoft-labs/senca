# 13. 運用

この章では、SENCA のノードを運用するための機能と手順を説明します。
ヘルスチェック、ログ、監視、イベントによる自動化、障害からの復旧、バックアップ、バージョンアップ、ノードのドレイン、停止のしかた、容量の見積もりを扱います。

- 関連するページ: [3. 設定](03-configuration.md)、[5. 録画](05-recording.md)、[9. クラスターとグリッド](09-cluster-grid.md)、[12. セキュリティ](12-security.md)、[15. 管理 API と SDK](15-api-and-sdks.md)
- 設計の背景: [ADR-0005 録画の形式とインデックス](../../dev/adr/0005-recording.md)、[ADR-0009 分散の制御プレーン](../../dev/adr/0009-cluster.md)、[ADR-0013 グリッド](../../dev/adr/0013-grid.md)

## 13.1 起動と終了コード

| 終了コード | 意味 |
|---|---|
| 0 | 正常終了（SIGTERM・SIGINT を受けた後） |
| 1 | 起動中の失敗（`fatal: ...`。ファイルが読めない、ポートで待ち受けできない、制御状態のログが途中で壊れている、クラスターシークレットが短いなど） |
| 2 | 設定の誤り（未知のオプション、検査に通らない値） |
| 70 | クラスターで Raft の保存に失敗した（書き込めない状態で動き続けることはしません） |

## 13.2 ヘルスチェック

| パス | 認証 | 応答 |
|---|---|---|
| `GET /healthz` | 不要 | HTTP で応答できれば常に `200 ok` |
| `GET /readyz` | 不要 | 準備ができていれば `200 ready`、それ以外は `503` |

- 単一ノードでは、起動時の処理（制御状態の読み込み、録画の復旧、待ち受けの開始）が終わると ready になります。
- クラスターでは、リーダーが決まり、自ノードの登録（最初のノードなら初期化も）が合意された後に ready になります。
- 終了のシグナルを受けると、`/readyz` は 503 を返します。
- **クラスターでは、過半数のノードとの通信が途絶えると 503 になります。** リーダーは過半数の投票者からの応答を、フォロワーは
  リーダーからのメッセージを最後に受け取ってから **4 秒**を超えると、自分に割り当てられたワークロード
  （pull の入力・push の出力・パイプライン）を停止し（フェンシング。ログに `grid: fenced`）、`/readyz` は 503 を返します
  （書き込みの API も 503 になります）。通信が回復すると 200 に戻り、割り当てられたワークロードを再開します（ログに
  `quorum contact restored`）。起動直後も、リーダーと通信できるまでは 503 です。
- 単一ノードでは、一度 ready になると終了まで 200 のままです。ドレイン（[13.9](#139-ノードのドレイン)）は ready に影響しません。

curl の入っていないコンテナイメージでも使えるように、ヘルスチェック用のコマンドを用意しています。

```sh
senca-node --healthcheck http://127.0.0.1:8080/readyz
```

- `--healthcheck` は**最初の引数**に書きます（他のオプションと一緒には使えません）。URL を省略すると `http://127.0.0.1:8080/readyz` を確認します。
- 対応するのは平文の `http://` だけです。`HTTP/1.1 200` が返れば終了コード 0、それ以外は 1、URL の形式が誤っていれば 2 で終了します。
- Docker イメージの `HEALTHCHECK` は、このコマンドを 10 秒ごとに実行します。

## 13.3 ログ

### ノードのログ

- 既定: 標準エラー出力に `RFC 3339 の時刻 + 空白 + 本文` の形式で出力します。
- `--log-json`: 標準出力に 1 行 1 JSON（`{"ts": "...", "node": "<ノード ID>", "msg": "..."}`）で出力します。

```
{"msg":"senca-node 0.0.0 started (node f1be5f27675d35f8dd72b88676be8754)","node":"f1be5f27675d35f8dd72b88676be8754","ts":"2026-11-03T01:11:38.915Z"}
```

`--log-json` を指定すると、ノードのすべてのログが標準出力の JSON になります。これには、最初の管理者トークンの作成、
`codec worker unavailable: ...`、`fatal: ...`（起動の失敗。ノード ID が決まる前は `node` が null）、設定の誤り、
codec worker・capture worker の標準エラー出力（ノードが 1 行ずつ読み取って `msg` に入れます。1 行 4096 バイトまで）も含まれます。
`--log-json` を指定しない場合、worker の出力は標準エラー出力にそのまま出ます。

主なログの内容: 待ち受けの開始、配信者の接続（`publisher attached`）と切断、録画の失敗、復旧の処理
（`recovery: ...`）、保持期間による削除（`retention: deleting recording ...`）、認証の失敗の理由と request_id、
入力・出力の再接続時のエラー、クラスター・グリッドの出来事（`grid: node ... is down` など）。
stream key やトークンの値はログに出力しません。

### 監査ログ

`data_dir/audit.log` に、状態を変更する API の操作を 1 行 1 JSON で追記します（形式は [12. セキュリティ](12-security.md#1212-監査ログ)）。
ノードは書き込みのたびにファイルを開き直すので、`mv` でローテーションしてかまいません（logrotate なら `create` 方式）。
ノード自身はローテーションしないので、ファイルサイズの管理は運用側で行ってください。書き込めないときはノードのログに
`audit log write failed: ...` と出力されます（API の操作自体は失敗しません）。

## 13.4 監視用の API

いずれも `node:admin` が必要です（`capabilities` だけは認証のみで使えます）。

| パス | 内容 |
|---|---|
| `GET /api/v1/nodes` | 登録されたノードの一覧: `id`・`name`・`draining`・`registered_at`・`labels`・`live_streams`（応答したノード自身の分だけを数えます）・`self`・`relay`（自ノードの中継の状態） |
| `GET /api/v1/nodes/{id}` | 1 つのノード |
| `GET /api/v1/grid` | グリッドの状態: `scheduler`（配置を決めているノード。リーダーに問い合わせたときだけ）、ノードごとの `up`・`draining`・`roles`・`labels`・`capacity`・`reserved`・`gpus`（セッション数と予約）・`capture`・`usage`（ハートビートで報告された実際の使用量）・`last_heartbeat`・`workloads`、ワークロードごとの `state`（`running`・`degraded`・`pending`・`unschedulable`）・`node`・`device`・`level`・`reason` |
| `GET /api/v1/devices` | このノードのコーデックのプロバイダー（使えるかどうかと理由）、サンドボックスの状態、キャプチャデバイス |
| `GET /api/v1/capabilities` | このノードが対応する受信方式・出力・コーデック（`codecs.transcode` は読み込めたもの）・機能の一覧 |

ストリームごとの状態は、`GET /api/v1/streams/{id}` の `observed_state`（`live`・`waiting_input`・`stopped`）と `live`
（開始時刻・ビットレート・トラック）で確認します。入力・出力は `status`（`state`・`last_error`・接続回数）で確認します。

Prometheus などのメトリクスのエンドポイントは、現在ありません。上の API を定期的に取得して監視してください。

## 13.5 イベント（SSE）による自動化

`GET /api/v1/events`（`stream:read`）は、合意されて適用された変更を Server-Sent Events で配信します。

```sh
curl -sN -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/v1/events
```

```
event: node.updated
id: 10
data: {"data":{"draining":true},"occurred_at":"2026-11-03T01:12:07.603Z","resource_id":"f1be5f27675d35f8dd72b88676be8754","type":"node.updated"}
```

- `id` は制御ログ上の位置です。届くのは自分のテナントのイベントだけです。ノード・デバイス・グリッドのイベント（`node.*`・`device.*`・
  `grid.decisions`・`stream.owner`）は、`node:admin` を持つ場合だけ届きます。
- 15 秒ごとに keep-alive を送ります。
- `Last-Event-ID` を付けて再接続したとき、その位置がノードの現在の位置より古ければ、すぐに `resync` が届きます
  （過去のイベントは再送しません）。読み取りが遅れてイベントを取りこぼしたときも、`resync` を送って接続を閉じます。
- 部屋のイベント（`room.started`・`room.connection.created` など）は `id` を持たず、取りこぼしても再送されません。

自動化の基本的な流れ: 接続したときと `resync` を受けたときに REST で一覧を取得し直し、それ以降はイベントで差分を追います。
イベントの種類の一覧は [15. 管理 API と SDK](15-api-and-sdks.md) にあります。

## 13.6 障害からの復旧

ノードは起動のたびに、録画の復旧処理を行います。

1. 削除の途中だった録画の削除を完了します。
2. `recordings/*/index.jsonl` を読み、`end` 行が無い（書き込み途中の）インデックスは、末尾の書きかけの行を切り捨て、
   `end` 行（`state: "interrupted"`、終了時刻は最後のセグメントの終わり）を追記して閉じます。制御状態の録画も
   `interrupted` にします。ログ: `recovery: recording <ID> closed as interrupted (<N> segments)`。
3. それでも制御状態で `recording` のままの録画（インデックスが無いものなど。このノードの分）を `interrupted` にします。
4. どのインデックスからも参照されていないセグメントを `segments/{stream}/orphans/{run}/` へ移します（削除はしません）。
   読めないインデックスが 1 つでもあると、この隔離は行いません（参照を失わないためです）。読めないインデックス自体には手を加えません。
5. `--verify-recordings` を指定すると、インデックスにあるすべてのセグメントの SHA-256 を照合し、一致しないものをログに出力します。

`interrupted` の録画も、それまでのセグメントは VOD として再生・書き出しできます。
例えば、録画中に SIGKILL で停止して起動し直すと、録画は `interrupted` になり、それまでのセグメントが残ります。
SIGTERM で停止した場合は `finalized` で閉じられます。

制御状態（単一ノードの `control/log`）は、末尾の書きかけのレコードを切り捨てて読み込みます。途中のレコードが壊れている場合は
起動しません（黙って捨てることはしません）。

## 13.7 バックアップ

| 対象 | 重要度 | 内容 |
|---|---|---|
| `control/`（単一ノード: `log`・`snapshot.json`） | 必須 | 制御状態のすべて（ストリーム・トークン・録画の記録・予約・入力・出力・秘密値・再生用の鍵） |
| `control/secret-key` | 必須（単一ノード） | 秘密値を復号する鍵。失うと登録した秘密値は復元できません。クラスターでは秘密値をクラスター共通の鍵（クラスターシークレットで暗号化して制御状態で複製）で暗号化するため、クラスターシークレット（`secret_file`）を別に安全に保管してください（[12. セキュリティ](12-security.md)） |
| `recordings/` と `segments/` | 録画を保護するなら必須 | インデックスとセグメントは**組にして**バックアップします（インデックスがセグメントを参照するため） |
| `snapshots/` | 任意 | 定期的に保存した静止画 |
| `node-id` | 推奨 | ノードの ID。変わると別のノードとして登録されます |
| `audit.log` | 運用方針による | 監査ログ |

- 一貫したバックアップを取るには、ノードを停止してからコピーするか、ファイルシステムのスナップショット（LVM・ZFS・btrfs など）を使ってください。
  動作中に `control/` をコピーすると、スナップショットの作成（`snapshot.json` を書き出してログを空にする処理）と重なり、
  変更を取りこぼすことがあります。
- 復元するときは、ノードを停止し、データディレクトリをまとめて戻してから起動します。書き込み途中の録画は、起動時の復旧処理で閉じられます。
- バックアップには、再生用の鍵・暗号化した秘密値・トークンのハッシュが含まれます。データディレクトリと同じように保護してください
  （[12. セキュリティ](12-security.md#128-データディレクトリの保護)）。
- クラスター: 制御状態は全ノードに複製されていますが、録画は録画したノードのディスクにだけあります。録画のバックアップは各ノードで取ってください。
  動作中のクラスターの 1 台に、Raft の保存データ（`control/raft/`）を古いバックアップから戻してはいけません（投票者は永続化した状態を
  失わない、という Raft の前提が崩れます）。クラスター単位での復元方法は [9. クラスターとグリッド](09-cluster-grid.md) を見てください。

## 13.8 バージョンアップ

現在、バージョン間でのデータの互換性は保証していません。現在のデータ形式について、次のことが分かっています。

- 制御状態のログは、コマンドを `op` の名前で表した JSON です。制御状態の項目の多くは省略時に既定値で読み込みますが、
  古いバージョンは未知の `op` を読めず、起動しません（`control log record N: ...`）。**ダウングレードはできない**ものと考えてください。
- 録画のインデックスは、`begin` 行に `schema`（現在は 1）を持ちます。未知の `schema` のインデックスには復旧処理で手を加えず（`left untouched`）、
  その場合は孤立したセグメントの隔離も行いません。
- `senca-node` と `senca-codec-worker` は、バージョン付きのプロトコルで通信します。**この 2 つは必ず同じバージョンにそろえて入れ替えてください。**
- クラスターで、バージョンの異なるノードを混在させる運用には対応していません。

手順（単一ノード）:

1. バックアップを取ります（[13.7](#137-バックアップ)）。
2. ノードを SIGTERM で停止します（録画は `finalized` で閉じられます）。
3. `senca-node`・`senca-codec-worker`（使っていれば `senca-capture-worker` も）を入れ替えます。
4. 起動し、`/readyz` とログ（`recovery: ...`・`fatal: ...`）を確認します。

## 13.9 ノードのドレイン

ドレイン（drain）は、ノードを保守などで止める前に、新しい処理を受け付けないようにして、処理を他のノードへ移す操作です。

```sh
curl -s -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/v1/nodes/$NODE/drain     # 202
curl -s -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/api/v1/nodes/$NODE/undrain   # 202
```

- `node:admin` が必要です。ノードの `draining` が true になり、`node.updated` イベントが送られます。
- グリッドは、このノードに新しいワークロード（pull 入力・push 出力・パイプライン・部屋・メディアパイプライン）を配置しなくなり、
  配置済みのワークロードのうち移せるものを他のノードへ移します（[9. クラスターとグリッド](09-cluster-grid.md)）。
- **ドレイン中のノードは、新しい配信者の接続を拒否します。** RTMP の publish は `NetStream.Publish.Rejected`（説明は
  `this node is draining; publish to another node`）、SRT の publish はハンドシェイクで拒否（理由 1503）します。WHIP の
  `POST /whip/{stream}` は、ドレイン中でない別のノードの同じパス（そのノードの `peers[].api`）へ 307 でリダイレクトします
  （該当するノードが無ければ 503 と `Retry-After: 10`）。WHIP クライアントはリダイレクトに従います。RTMP・SRT の配信者には、
  ノードをロードバランサーや DNS から外したうえで、別のノードへ接続し直してもらってください。
- **接続済みの配信者と視聴者は切断しません。** `/readyz` も 200 のままです（ロードバランサーからは別途外してください）。
- 単一ノードでは移動先が無いため、ワークロードはそのまま残ります（ドレイン後も pull 入力は `running`、`/readyz` は 200 です）。
  新しい配信者は拒否します（WHIP は 503）。

デバイス（GPU・キャプチャデバイス）だけを止めるときは、`POST /api/v1/nodes/{node}/devices/{device}/disable` を使います（戻すときは `enable`）。

## 13.10 停止のしかた

SIGTERM または SIGINT（`Ctrl-C`）を受けると、ノードは次の順に終了します。

1. ログに `shutting down` を出力し、`/readyz` が 503 になります。
2. クラスターでは、ノード間の中継の接続に GoAway を送り、このノードが終了することを相手のノードに伝えます。
3. ストリームごとに作成途中のセグメントを閉じ、録画中のものをすべて `finalized` で閉じます（インデックスに `end` を書いて fsync）。
4. codec worker を停止します。
5. ログに `bye` を出力し、終了コード 0 で終了します。

- 配信者と視聴者の接続は、プロセスの終了とともに切れます。
- 終了処理には時間の上限を設けていません（通常はすぐに終わります）。Docker の `docker stop` は、既定では 10 秒後に
  SIGKILL を送ります。SIGKILL や停電で停止した場合は、次の起動時に復旧処理が行われます（[13.6](#136-障害からの復旧)）。

## 13.11 容量の見積もり

### ノードが登録する容量

| オプション | 既定 | 意味 |
|---|---|---|
| `--capacity-cpu-millis` | CPU 数 × 1000 × 90% | グリッドがワークロードに割り当てる CPU（OS や制御プレーンの分を残します） |
| `--capacity-memory-mb` | `MemTotal` の 85% | ワークロードに割り当てるメモリ |
| `--net-mbps` | 10000 | 送信・受信それぞれの帯域 |
| `--label KEY=VALUE` | なし | 配置の条件に使うラベル（`zone=a` など） |

GPU は、codec worker が検出したデバイスごとに、エンコード・デコードのセッション数として登録されます（エンコードは上限が分からなければ 8、
デコードは 16 以上）。登録された容量は `GET /api/v1/grid` の `capacity`・`gpus` で確認できます。

### グリッドが数える量

グリッドは、ワークロードごとに次の**見積もり（予約量）**を合計して配置を決めます。実際に測った使用量ではありません。

| ワークロード | CPU | メモリ | 帯域 |
|---|---|---|---|
| pull 入力 | 150 m | 64 MB | 受信 10 Mbit/s |
| キャプチャ入力 | 500 m | 64 MB | —（H.264/H.265 でエンコードするなら GPU のエンコード 1） |
| push 出力 | 100 m | 64 MB | 送信 10 Mbit/s |
| パイプライン | 処理ノードの数から計算（デコード 400 m、GPU でのデコードなら 100 m、合成・板書補正・拡大縮小・切り抜き 300 m など） | 処理ノードの数から計算 | 送受信 10 Mbit/s |
| 部屋（参加者の上限 N、既定 50） | 200 + 20N m | 64 + 2N MB | 受信 2N、送信 2N × min(N, 8) Mbit/s |

- **RTMP・SRT・WHIP の配信者（push での受信）と、HLS などの視聴者は、グリッドの予約に含まれません。** その分は、
  `--capacity-*`・`--net-mbps` を実際の性能より小さく登録して確保してください。
- 部屋の既定（50 人）では、送信 800 Mbit/s を予約します。`--net-mbps` を小さくすると、部屋を配置できない
  （`unschedulable`）ことがあります。部屋の `max_participants` を実際の人数に合わせてください。
- codec worker のプロセス数は `--codec-workers`（既定は CPU 数）です。パイプラインは、これとは別に 1 つにつき 1 プロセスを使います。
- 録画の書き込みキューの長さは `--record-queue` で指定します（[3. 設定](03-configuration.md)）。ディスクが遅いとキューがあふれ、
  録画に欠落（gap）が記録されます（ライブ配信は止まりません）。

### 参考値
