# REQ-005 GUI のパイプライン構築、ロジックと計算資源の分離、ノード障害時の継続

- 追加日: 2026-10-26（利用者の指示）
- 状態: 要件として受理。仕様 5 章・8 章を拡張する。

## 要件

1. カメラ・音声の **多重化・分離・合成・変換・外部ソフトウェアでの処理** を組み合わせたパイプラインを、GUI で簡単に組める（REQ-002 の管理画面）。
2. **ロジック（パイプライン定義）と計算資源（ノード）を分離する。** 定義は「何をするか」だけを持ち、「どこで動かすか」は制御面が決める。
3. リアルタイム配信・録画の処理を担うノードが落ちても、**他のノードへ振り直して処理を継続する。**

## パイプラインの部品（ノード種別）

| 種類 | 例 | 実装 |
|---|---|---|
| 入力 | RTMP / SRT / RTSP / WebRTC / MoQ / HLS pull、DeckLink、PaaS（REQ-001） | 自前プロトコル・ボード SDK |
| 分離（demux） | 映像・音声・字幕・メタデータを別トラックへ | 自前 |
| 多重化（mux） | 複数トラックを 1 つの出力へ。時刻を揃える | 自前 |
| 選択・切替 | 入力の切替（キーフレーム境界）、バックアップ入力への自動切替 | 自前 |
| 合成 | 映像の画面合成（PinP・並べる・文字・画像）、音声のミキシング | 自前（仕様 2.1） |
| 変換 | トランスコード、リサイズ、フレームレート・サンプルレート変換 | コーデックは外部、その他は自前 |
| 外部処理 | 利用者のソフトウェア（AI 処理・字幕生成など）に通して戻す | 隔離した外部プロセス（下記） |
| 出力 | 各プロトコル、HLS、録画、PaaS | 自前 |

- 定義は有向非巡回グラフ（仕様 5.1）。各部品は入力・出力の形式、時刻基準、バッファ上限を宣言し、つなげない組み合わせは保存時に拒否する。
- GUI はグラフ編集（部品を置いて線でつなぐ）。保存前に `POST /pipelines/{id}/validate` で検証し、`commit` で新世代として反映する。
- 部品ごとに「必要な資源」（CPU・GPU 種別・ボード・帯域）を宣言する。配置はそれを見て決める。

### 外部ソフトウェアの処理

- 外部処理は **SENCA の中核ではない利用者の拡張** として扱い、本番コアの自前実装の原則（仕様 2.1）とは分けて表示する。
- 隔離したプロセス（コンテナ）で動かし、権限・ファイル・ネットワーク・CPU/メモリを制限する（仕様 9.4）。
- 受け渡しは版付きの決まった形（未圧縮フレームを共有メモリ、または符号化済み AU をソケット）にする。期限を過ぎたフレームは捨て、外部処理の遅れでパイプライン全体を止めない（仕様 5.3）。
- 外部処理が落ちた・遅れたときの動き（素通し・黒画面・停止）を部品ごとに選べる。

## ロジックと計算資源の分離

- パイプライン定義は場所を持たない。制御面が **配置（placement）** を決め、ノードへ割り当てる（仕様 8.3）。
- 1 つのパイプラインを複数ノードに分けて置ける（例: 入力はエッジ、変換は GPU ノード、出力はリレー）。ノード間は `senca-relay` で AU を運ぶ。
- 割り当ては合意ログに記録し、所有権（owner / epoch / lease / fencing token、仕様 8.2）で 1 か所だけが実行する。

## ノード障害時の継続

ノードの lease が切れたら、制御面が別のノードに割り当て直し、新しい epoch で処理を再開する。

| 対象 | 振り直しの動き | 途切れ |
|---|---|---|
| pull 型の入力（RTSP、SRT caller、HLS pull、PaaS から取る） | 新しいノードが取り直す | 数秒 |
| push 型の入力（RTMP、SRT listener、WHIP） | 送り元に再接続してもらう。入口は LB / DNS で複数ノードへ向け、送り元の自動再接続を前提にする | 送り元の再接続まで |
| 変換・合成・外部処理 | 別ノードで部品を起動し、次のキーフレームから再開 | 数秒 |
| 出力（WebRTC / SRT / MoQ） | 視聴者・受け手は再接続・再交渉（暗号状態は引き継がない、仕様 8.3） | 再接続まで |
| HLS 出力 | 新しいノードが discontinuity を入れて続ける | セグメント 1〜2 本 |
| 録画 | 確定済みセグメントは残る。新しい owner が新 epoch で続け、欠落区間を索引に記録（仕様 8.4） | 欠落区間として記録 |

### 二重化（1+1）モード

途切れを許さない配信・録画のために、パイプラインごとに選べる。

- 同じパイプラインを 2 ノード（別障害ドメイン）で同時に動かす。
- 出力は片方を primary とし、primary が落ちたら secondary に切り替える（fencing で同時に公開しない）。
- 録画は両方が書き、セグメント単位（時刻と内容のハッシュ）で重複を除いて 1 本にする。
- 費用（資源）は約 2 倍。管理画面で明示する。

### 目標値（仕様 13.3 に追加）

| 項目 | 目標 |
|---|---|
| 振り直しによる再開（pull 入力・変換） | p95 10 秒以内 |
| 二重化モードの切替 | p95 1 秒以内、録画の欠落 0 |
| 二重公開・stale write | 0（AC-15） |

## 受け入れ試験（案）

| ID | 内容 | 合格条件 |
|---|---|---|
| AC-P10 | GUI で入力 2 つ → 合成 → 変換 → HLS と録画、を組んで反映 | API と同じ定義が保存され、再生・録画できる |
| AC-P11 | つなげない組み合わせ（コーデック不一致など）を保存 | 保存前に理由付きで拒否 |
| AC-P12 | 変換ノードを kill | 10 秒以内に別ノードで再開、録画に欠落区間が記録される |
| AC-P13 | 二重化モードで primary を kill | 視聴の途切れ 1 秒以内、録画の欠落 0、二重公開 0 |
| AC-P14 | 外部処理を止める・遅らせる | 選んだ動き（素通し等）になり、他の部品・テナントに波及しない |
