# REQ-002 制御 API の拡張と管理画面（GUI）

- 追加日: 2026-10-26（利用者の指示）
- 状態: 要件として受理。仕様書 v1.1 で 10 章・12 章に取り込む。

## 要件

1. **予定による操作を API で行える。** 例: 指定時刻に録画を開始・停止する、配信を開始・停止する、出力（PaaS 連携を含む）を切り替える。
2. **パイプラインとノードの管理を GUI で行える。** パイプライン（入力 → 変換 → 出力のグラフ）の作成・編集・状態確認、ノードの一覧・状態・drain・更新を画面から操作する。
3. GUI でできることは、すべて API でもできる（GUI は API の利用者の 1 つ）。

## API の追加（案）

| Method / Path | 動作 | 権限 |
|---|---|---|
| POST /schedules | 予定の作成（対象・操作・時刻・繰り返し・タイムゾーン） | stream:write |
| GET /schedules | 予定の一覧 | stream:read |
| GET/PATCH/DELETE /schedules/{id} | 取得・更新（If-Match）・削除 | stream:read / stream:write |
| GET /schedules/{id}/runs | 実行履歴と結果 | stream:read |
| POST /pipelines | パイプライン（DAG）の作成 | stream:write |
| POST /pipelines/{id}/validate | 検証のみ（仕様 5.1） | stream:read |
| POST /pipelines/{id}/commit | 新世代として反映（失敗時は旧世代を継続） | stream:write |
| GET /nodes/{id} | ノードの詳細（資源・ハードウェア・稼働中の処理） | 運用権限 |
| POST /nodes/{id}/undrain | drain の解除 | 運用権限 |
| GET /devices | 全ノードのハードウェア（GPU・キャプチャボード）一覧 | 運用権限 |

### 予定実行の決まり

- 予定は合意ログ（仕様 8.1）に保存し、実行は所有権（仕様 8.2）を持つ 1 ノードだけが行う。二重実行しない（fencing token を検証）。
- 時刻は UTC で保存し、繰り返しはタイムゾーン付きで解釈する（夏時間の重複・欠落の扱いを明記）。
- 制御面の障害で実行時刻を過ぎた場合の扱い（実行する猶予・諦める）を予定ごとに持つ。
- 各実行は operation として記録し、SSE イベントで通知する。

### 1 つの入力を複数の予約で共有する（時間の重なりあり）

例: 1 台のカメラに、予約 A（10:00〜12:00 録画）と予約 B（11:30〜13:00 録画と配信）がある。

- **入力は 1 本だけ取る。** 予約は入力の「購読者」。重なっても入力への接続（RTSP の pull など）は増やさない。
- **入力の起動・停止は参照カウント。** 最初の予約の開始前（準備時間 `pre_roll`、既定 30 秒）に取り始め、最後の予約の終了後（`post_roll`）に止める。予約の途中で入力が切れたら、各予約に欠落区間として記録する。
- **録画は予約ごとに独立した Recording。** ID・開始終了・保持期限・権限は別々。
- **重なった区間のメディアは共有する。** 同じ入力・同じ設定なら、確定済みの不変セグメント（仕様 8.4）を両方の Recording の索引から参照する。容量は 1 本分。参照カウントで、片方を削除してももう片方のセグメントは残す。
- **開始・終了の時刻は正確に。** セグメントはキーフレーム境界で切れるので、各 Recording の索引に「表示開始・終了の PTS」を持ち、再生・書き出し時に切り出す。必要なら境界の GOP だけ再エンコードした書き出しを選べる。
- **予約ごとに設定が違う場合。** 解像度・ビットレート・出力先が違えば、共有するのは入力までで、変換以降は予約ごとに分岐する（パイプラインの分岐、REQ-005）。
- **競合の検出は登録時に。** 予約の作成・変更時に、時間の重なりと必要な資源（GPU 枠・帯域・カメラの同時接続数・PTZ などの排他的な操作）を検査する。足りない・ぶつかる場合は、優先度の決まりで解決するか、理由付きで拒否する（409）。
- **途中変更。** 実行中の予約の終了時刻の延長・短縮、片方だけの取り消しは、他の予約に影響しない。

| Method / Path | 動作 |
|---|---|
| GET /inputs/{id}/reservations | その入力に関わる予約の一覧（時間帯の重なりを表示） |
| POST /schedules/check | 作成前の検査（重なり・資源・競合）。副作用なし |

試験（案）: AC-P20 予約 A・B が重なる録画で、入力接続は 1 本、各 Recording が指定時刻どおりに再生でき、A を削除しても B の重なり区間が再生できる。

## GUI（管理画面）

- 置き場所: `apps/console/`（モノレポ内）。
- 公開 API（`/api/v1`）だけを使う。内部 API を持たない。
- 認証は管理 API と同じ（OIDC）。権限で表示と操作を分ける。
  - 2026-11-04 追記（利用者の指示）: OIDC に加えて、SENCA の利用者のアカウント（パスワードと TOTP の MFA）も用意する。どちらも
    ログインのセッション（`sencas_`）になり、API トークン・JWT と同じ `Authorization: Bearer` で使う（ADR-0017）。
- 画面: ダッシュボード、配信（stream）、パイプライン編集（グラフ）、録画と予定、ノードとデバイス、連携先（REQ-001）、監査ログ。
- 外部に公開するときは Cloudflare Access などの前段を通す（社内の方針）。
