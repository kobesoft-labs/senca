# REQ-010 性能とスケール（マルチスレッド・マルチ CPU・ノードの追加で速くする）

- 追加日: 2026-10-26（利用者の指示「パフォーマンスを上げるために、マルチスレッド、マルチ CPU などに対応し、ノードを指定したスケールまで速度を上げる。最終的には絶対に実装」「ノードはなるべくコピーレス、ネットワークレスでありながら、マルチスレッド、グリッドコンピューティングに対応させる」）
- 状態: 要件として受理。**必須**（最終形で満たす）。ロードマップの各段で少しずつ入れ、M14 の負荷試験で確かめる。

## 要件

| ID | 内容 |
|---|---|
| R10-1 | **1 台の CPU を使い切る。** 受信・パケット化・配信・録画はスレッドをまたいで並列に動く（stream ごと、接続ごと）。1 つの stream の処理が他の stream を待たせない |
| R10-2 | **変換（デコード・エンコード・画像処理）を CPU のコア数ぶん並べる。** codec worker は数を指定できるプールにし、コア数に合わせて増やせる。重い変換が受信・配信を遅らせない（仕様 5.3 のライブ優先） |
| R10-3 | **GPU などのハードウェアを使える**（REQ-004）。CPU と GPU の枠を資源として数える |
| R10-4 | **ノードを足すと速くなる。** 指定した規模（同時 stream 数・同時視聴数・同時変換数）まで、ノードを追加して処理量を増やせる（M9 の分散）。配置は資源の空きに応じて決める |
| R10-5 | **目標の規模を設定できる。** 「この規模まで」を設定・API で指定でき、足りないときは不足を知らせる（自動でノードを増やす連携は REQ-001・REQ-003 と合わせて） |
| R10-7 | **コピーしない。** 受け取ったメディアは一度だけ組み立て、あとは参照で共有する（ライブ・録画・視聴者への配信で同じバッファ）。形を変える所（TS への多重化、暗号化など）以外で中身をコピーしない。多数の視聴者には 1 つのバッファを配る |
| R10-8 | **ノードの中でネットワークを使わない。** ノード内の部品（受信・多重化・録画・配信・codec worker）は、同じプロセスのメモリ・パイプ・共有メモリでつなぐ。ループバックの TCP や外部のブローカー（Redis・Kafka など）を通さない |
| R10-9 | **グリッドで動く。** 複数のノードが 1 つの計算資源として働く（M9）。仕事は**データのある所で**行い、ノード間で動かすのは圧縮されたメディアだけ（生のフレームは動かさない）。足りないときだけ他のノードへ分ける（配信の木、GPU ノードでの変換など） |
| R10-6 | **測って確かめる。** 1 ノードあたりの処理量（stream 数・ビットレート・変換数）と、ノード数に対する伸び（線形からのずれ）を負荷試験で測り、適合台帳に記録する |

## 置き場所（ロードマップとの対応）

| 段 | 入れること |
|---|---|
| M1〜M3（済） | tokio のマルチスレッド実行、stream・接続・録画（チェーン）ごとのタスク、ライブと録画のキュー分離 |
| M4 | codec worker のプール（数を指定、既定はコア数から決める）、ジョブの待ち行列とテナントごとの公平さ。ADR-0012 の M4-5（ノード内のコピー削減と計測） |
| M5・M13 | 合成・変換の並列化、GPU の枠（REQ-004） |
| M9 | 複数ノード（配置・振り直し・資源の予約）、ノードの追加で処理量が増えること |
| M14 | 負荷試験（R10-6）、プロファイリングと改善 |

## 受け入れ試験（案）

| ID | 内容 | 合格条件 |
|---|---|---|
| AC-R10-01 | 1 ノードで stream 数を増やす | CPU 使用率がコア数に応じて上がり、1 stream あたりの遅延が目標内（値は P0 で決める） |
| AC-R10-02 | サムネイル・変換を同時に多数 | worker プールの数に比例して処理量が増え、ライブの遅延・途切れが増えない |
| AC-R10-03 | ノードを 1 → 2 → 4 台 | 処理量がノード数にほぼ比例して増える（ずれは記録する） |
