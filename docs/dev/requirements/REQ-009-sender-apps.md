# REQ-009 送り手のアプリ（Web カメラ・PC/Mac・スマートフォン・タブレット）

- 追加日: 2026-10-26（利用者の指示）
- 状態: 要件として受理。ロードマップ M15。WHIP は M8（WebRTC）の後。

## 要件

| ID | 内容 |
|---|---|
| R9-1 | PC・Mac の **Web カメラ**から配信できる（ブラウザ、アプリ不要） |
| R9-2 | **PC・Mac のアプリ**から配信できる（カメラ、マイク、画面、ウィンドウ） |
| R9-3 | **スマートフォン・タブレット**（iOS / iPadOS / Android）のアプリから配信できる |
| R9-4 | アプリは **弊社がアプリストアに出す**。**エンドポイントを入れれば使える**（QR コードでも） |
| R9-5 | アプリは **標準規格に沿う**。SENCA 以外の標準準拠サーバーにも送れる |
| R9-6 | **カメラ制御**: 遠隔からズーム・フォーカス・露出・ホワイトバランス・ライト・カメラ切替・解像度・フレームレート・ビットレート。標準の制御プロトコルへの対応も検討（下記） |

## 方式

### 送る規格（優先順）

| 規格 | 用途 | 時期 |
|---|---|---|
| **WHIP**（RFC 9725、WebRTC） | 基本。「URL＋Bearer トークン」だけで送れる。低遅延 | M8 の後 |
| **SRT**（caller） | 不安定な回線、拠点間 | M7 の後（アプリ側は先に作れる） |
| **RTMPS / RTMP** | 既存の配信サービス・機器との互換 | 早期 |

- コーデック: H.264 + AAC/Opus を基本。対応端末では H.265、ロイヤリティフリーの指定時は VP8/VP9/AV1 + Opus（REQ-007、端末のハードウェアエンコーダーの有無で選ぶ）。
- 入力の設定は 1 つの文字列で済むようにする: `https://…/whip/{stream}`＋トークン、`srt://…?streamid=…`、`rtmps://…/live/{key}`。

### 「エンドポイントを入れたら使える」

- SENCA の制御 API が **送り手用の資格情報** を発行する（M3）: WHIP URL と短命のトークン、または SRT / RTMPS の URL と鍵。
- 管理画面は **QR コード** を出す。中身は標準の URL（WHIP / SRT / RTMPS）そのもの。SENCA 固有の形式にしない（他社サーバーでも使えるように、R9-5）。
- 任意で「設定 URL」（HTTPS、JSON、短命）も出せる: 推奨の解像度・ビットレート・コーデック・制御の接続先をまとめて渡す。標準外なので、無くても送れることを保つ。

### アプリの作り方（ADR で確定）

| 層 | 案 |
|---|---|
| 取り込み・ハードウェアエンコード | 各 OS の標準: iOS/iPadOS/macOS = AVFoundation・VideoToolbox・ScreenCaptureKit、Android = Camera2/CameraX・MediaCodec・MediaProjection、Windows = Media Foundation |
| 送信（WHIP/WebRTC・SRT・RTMP） | **Rust の共通部品 senca-sdk**（仕様 11 章、C ABI）を全 OS で共有。WebRTC はサーバーと同じ自前実装（M8）。ブラウザは標準の RTCPeerConnection |
| 画面 | SwiftUI（Apple）、Jetpack Compose（Android）。Windows/Linux は後続 |
| 置き場所 | `apps/ios`、`apps/android`、`apps/desktop`、`apps/web-sender`、`crates/senca-sdk` |

### カメラ制御

| 方向 | 方式 |
|---|---|
| SENCA → アプリ | 制御 API 経由。WHIP 接続中は WebRTC DataChannel、それ以外は WebSocket で指示を届ける。権限は stream ごと |
| 既存の操作盤・スイッチャー → アプリ | **VISCA over IP**（Sony 公開仕様）の受け口をアプリに持たせる案。ズーム・フォーカス・露出・プリセット。パン・チルトはデジタル（切り抜き）で模擬 |
| SENCA → IP カメラ | **ONVIF**（Profile S の PTZ・Imaging）クライアント。仕様 1.2 で「全カメラの ONVIF 制御」は初期対象外なので、相互接続を確認した機種から |

- 制御のコマンドは認可（仕様 9.2）を通し、監査ログに残す。
- 端末の権限（カメラ・マイク・画面収録）は OS の許可を必ず通す。バックグラウンドでの送信は各ストアの規約に従う。

## ストア公開に向けた注意

- App Store / Google Play の審査: カメラ・マイク・画面収録の利用目的の説明、プライバシー表示（収集するデータ）、バックグラウンド動作の正当性。
- 暗号の輸出規制の申告（WebRTC の DTLS-SRTP、TLS を使うため）。
- コーデックのライセンス: 端末の OS が持つエンコーダーを使う場合と、アプリに同梱する場合で扱いが違う（REQ-007）。
- アプリ名・ID・署名は弊社のアカウントで管理する。

## 追記（2026-10-26）: センサーと複数カメラ

| ID | 内容 |
|---|---|
| R9-7 | スマホ・タブレットの **深度**（LiDAR・TrueDepth・ToF）、**GPS**、加速度・ジャイロ・方位・気圧などのセンサーを、映像と同じ時刻基準で送れる |
| R9-8 | **前後のカメラを同時に** 使える端末では、2 本の映像として同時に送れる（iOS: AVCaptureMultiCamSession、Android: 同時カメラ対応機種） |

### 運び方

| データ | 共通メディアモデル（仕様 4.1） | WebRTC | SRT / TS | MoQ | HLS / 録画 |
|---|---|---|---|---|---|
| 前後カメラ | 映像 Track を 2 本 | 映像トラック 2 本 | 映像 PID 2 本 | Track 2 本 | 別の Rendition / 別の録画トラック |
| 深度 | 映像 Track（種別 depth） | 映像トラック | 映像 PID | Track | 別トラック |
| GPS・IMU 等 | 時刻付きメタデータ Track | DataChannel（時刻付き） | メタデータ PES（ISO/IEC 13818-1 の metadata、または SMPTE KLV） | Track | timed metadata（ID3）・索引の別ファイル |

- **深度の符号化**: 16 ビットの深度を、標準コーデックで運べる形に詰める（例: HEVC Main 10 / 16 ビットの単色、または 8 ビット 2 面への分割）。可逆か不可逆かと、深度の単位・範囲・カメラの内部パラメーターはメタデータで一緒に送る。方式は ADR で決め、受け側で元の値に戻せることを試験する。
- **時刻**: すべてのトラックに同じ端末の capture 時刻を付ける（仕様 4.2 の capture_time_ns）。センサーの値は、取得時刻と映像フレームとの対応を受け側で取れるようにする。
- **端末ごとの違い**: 同時カメラ・深度・センサーの有無は端末で違う。アプリは送れるものを能力として送り、SENCA は capabilities として記録する。

### プライバシー

- GPS などの位置情報は個人情報。**送るかどうかは端末側で明示的に選ぶ**（既定は送らない）。
- SENCA 側では、位置情報のトラックを閲覧する権限を映像とは分ける（例: `telemetry:read`）。保存期間も別に設定できる。
- 公開配信では、位置情報を既定で外す。
