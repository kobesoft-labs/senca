# ADR-0004 コーデックの選定と特許の方針

- 状態: 採用（2026-11-02、利用者の指示「特許の問題があるので、Intel/AMD/NVIDIA などのライブラリで H.264/H.265 を実装」）

## 決定

1. **H.264 / H.265 のエンコード・デコードは、GPU ベンダーのハードウェアコーデックだけで行う。** ソフトウェアの H.264/H.265 コーデック（libavcodec、OpenH264、x264、x265 など）を製品に入れない・読み込まない。

   | ベンダー | API | 読み込むライブラリ（実行時に dlopen） | 用途 |
   |---|---|---|---|
   | NVIDIA | NVENC / NVDEC（Video Codec SDK） | `libnvidia-encode.so.1`、`libnvcuvid.so.1`、`libcuda.so.1` | エンコード・デコード |
   | Intel | oneVPL（Quick Sync） | `libvpl.so.2` | エンコード・デコード |
   | AMD | AMF | `libamfrt64.so.1` | エンコード・デコード |
   | Intel / AMD（Linux） | VA-API | `libva.so.2`、`libva-drm.so.2` | エンコード・デコード |
   | Apple（開発・SDK） | VideoToolbox | システムのフレームワーク | エンコード・デコード |

   ハードウェアの実装はベンダーが特許の対価を払った製品の機能として提供されている。ただし**配信サービス・コンテンツ配布に関わる特許料（例: Via LA の AVC/HEVC のプール）はハードウェアの購入では済まない場合がある**。この判断は法務確認の対象とし、ライセンス台帳（`docs/licenses/README.md`）に一次資料を残す。

2. **H.264/H.265 のビットストリームの解析・形式変換（Annex B ⇔ 長さ前置、SPS/PPS/VPS の解析、パケット化）は自前で行う。** これはコーデック（符号化・復号）ではなく、仕様 2.1 で自社実装とされた範囲。

3. **AAC はそのまま通す（パススルー）だけ。** AAC のエンコード・デコードを製品に入れない。音声の変換が要るときは Opus に変換する（AAC の入力を復号する必要がある場面は、ハードウェア・外部サービスが無ければ「対応しない」と理由付きで拒否）。

4. **ロイヤリティフリーとして提供されているコーデックはソフトウェアで使ってよい**（REQ-007）。codec worker が実行時に読み込む: dav1d（AV1 復号、BSD-2）、SVT-AV1（AV1 符号化、BSD-3＋特許許諾）、libvpx（VP8/VP9、BSD-3）、libopus（Opus、BSD-3）。

5. 外部コーデックは別プロセスの `senca-codec-worker` で動かす（仕様 3.1・9.4、AC-17）。ノード本体は外部コーデックを読み込まない。

6. ハードウェアの無い環境では、H.264/H.265 の変換を要求する処理（静止画・サムネイル・トランスコード）は `CAPACITY_UNAVAILABLE`（503）または変換計画での拒否として理由を返す。黙って劣化させない。

## 試験

開発機（x86_64、GPU なし）では、ハードウェアのプロバイダーはビルドと「装置なし」の検出までを試験する。実機での試験は型番・ドライバー版を相互接続表に記録し、実機の無いものは「未検証」と表示する（REQ-004）。
