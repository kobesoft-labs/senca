# ADR-0017 利用者のアカウント・ログインのセッション・OIDC

- 状態: 採用（2026-11-04、利用者の指示）
- 関係: 仕様 9.2・9.3・9.5・10.1、REQ-002（管理画面の認証）、ADR-0002・ADR-0005・ADR-0009

## 背景

管理 API の認証は、API トークン（`senca_`）と、ローカルの JWKS で確かめる JWT だけだった。管理画面はトークンを貼り付けて使っていた。
REQ-002 は管理画面の認証を OIDC としているが、IdP の無い小さな構成でも使えるように、利用者の指示で次の 2 つを両方用意する。

1. SENCA の利用者（パスワードと TOTP の MFA）
2. OIDC のシングルサインオン（Google Workspace・Microsoft Entra ID・Keycloak・Auth0 など）

API トークンと JWT はそのまま使える。どれも同じ `Authorization: Bearer` で受ける。

## 決定

### 利用者（制御状態）

- 利用者は制御状態（`ControlState::users`）に置き、Raft で複製する（トークンと同じ。どのノードでもログインでき、どのノードでも確かめられる）。
  テナントごとで、別のテナントからは 404。
- 項目: ID・利用者名（ASCII の英数字と `._@+-`、1〜64 文字、テナントの中で大文字・小文字を区別せずに一意）・メールアドレス（任意、テナントの中で一意）・
  表示名・パスワードのハッシュ（任意。OIDC だけの利用者は持たない）・役割（`admin`・`operator`・`viewer`）と個別の権限・無効・`must_change_password`・
  MFA（封じた TOTP の秘密・最後に使った区切り・回復コードのハッシュ）・OIDC の結び付き（IdP と `sub`）・世代・作成・更新・最後のログイン・パスワードの変更の時刻。
- 権限は役割と個別の権限の和。`tenant:admin` は今までどおり `node:admin` 以外を含む。セッションの権限は**その時点の利用者**から決める（役割の変更はすぐ効く）。
- **最後の管理者**: テナントに有効な管理者（`tenant:admin` を持つ利用者）がいるとき、最後の 1 人の削除・無効化・降格は 409（`apply` で検査）。
  管理者の利用者がいないテナント（トークンだけで運用しているテナント）では制限しない。トークンの「最後の管理者トークン」の規則とは別に数える
  （管理画面に入れなくなるのは利用者の側だけで決まるため）。
- **権限の昇格の拒否**（API の側）: 渡せる権限は自分が持つものまで（トークンと同じ）。`node:admin` は `node:admin` を持つ主体だけが渡せる。
  さらに、自分の持たない権限を持つ利用者は変更・削除・パスワードの再設定・MFA の解除・セッションの失効ができない（403）。
  `tenant:admin` だけの管理者が `node:admin` の利用者のパスワードを再設定して乗っ取ることを防ぐ。

### 暗号の部品（自分で書かない）

| 用途 | 部品 | 決め事 |
|---|---|---|
| パスワード | `argon2` 0.5（RustCrypto） | Argon2id、m=19 MiB・t=2・p=1（OWASP の推奨の 1 つ）、利用者ごとに 16 バイトの乱数の塩、PHC 文字列。弱いパラメーターのハッシュはログインのときに作り直す（`needs_rehash`） |
| TOTP | `totp-rs` 5（HOTP の計算） | RFC 6238、SHA-1・6 桁・30 秒、前後 1 区切りのずれを許す。秘密は 20 バイトの乱数。どの区切りも同じだけ計算し、`subtle` で比べる |
| 回復コード | `getrandom`・`sha2` | 10 個、各 16 文字（31 文字の英数字から、約 79 bit）。保存は `SHA-256("senca-recovery-code/v1\0" ‖ 利用者 ID ‖ 正規化したコード)`。乱数の強さが十分なので遅いハッシュは使わない（トークンと同じ考え） |
| セッションの値 | `getrandom`・`sha2` | `sencas_` + 32 バイトの乱数（base64url）。状態には SHA-256 だけ |
| 封じた値 | `aes-gcm`（既存） | 秘密値の鍵（分散ではクラスタ共通のデータ鍵、ADR-0009）。用途ごとに関連データを分ける（`senca/auth-mfa/v1` など） |
| ID トークン | `ed25519-dalek`・`p256`・`rsa`（既存の JWT の検証） | 鍵が算法を決める（`none`・HS 系は使えない） |

- パスワードは Unicode の文字数で 12〜256 文字、利用者名・メールアドレスと同じものは不可。**正規化（NFKC）はしない**（依存に正規化の crate が無いため。
  入れるときは、既存のハッシュとの互換のために「正規化した形と、そのままの形の両方で照合する」移行が要る）。
- `argon2` と `blake2` は、開発用のビルドでも最適化する（`[profile.dev.package.*]`）。最適化なしでは 1 回に数秒かかり、試験が成り立たないため。
- Argon2id の計算は同時に 4 つまで（19 MiB × 同時の数でメモリを使うため）。それを超えた要求は待つ。

### セッション

- `POST /auth/login`（とその続き）・`POST /auth/exchange` が返す不透明な値。API トークンとは接頭辞で分ける（`senca_` と `sencas_`）。
  状態の `sessions` は値の SHA-256 をキーにして引く（値は 256 bit の乱数なので、引く時間から分かることは無い。念のため定数時間でも照合する）。
- 期限は 2 つ。**待ち時間**（最後に使ってから、既定 8 時間、`--auth-session-idle`）と**寿命**（作ってから、既定 7 日、`--auth-session-lifetime`）。
  既定の理由: 8 時間は 1 日の作業の長さ（翌朝には入り直す）。7 日は、盗まれたセッションが使える長さの上限を週単位に抑えるため。
  値は作ったときにセッションに書く（ノードの設定がずれても、全ノードで同じ判定になる）。
- **最後に使った時刻**は、要求のたびには書かない。前に記録した時刻から「待ち時間の 1/16 を 30 秒〜5 分に収めた間隔（待ち時間の 1/4 まで）」が
  過ぎたときだけ、`TouchSession` を裏で提案する（同じセッションの提案は、その間隔の中では 1 度だけ）。既定ではセッション 1 つにつき 5 分に 1 回まで。
  その分、待ち時間の判定は最大でその間隔だけ早めに切れうる。
- 失効: ログアウト、パスワードの変更（変えたセッションは残す）・管理者による再設定（すべて）、利用者の無効化・削除、役割・権限の変更（すべて）。
  MFA の変更では失効させない。利用者ごとに 20 まで（古いものから消す）。期限の切れたものは、保持期間の掃除の周期（`--retention-sweep`）で `ExpireSessions` を提案して消す
  （認証は期限を自分でも確かめるので、掃除が遅れても通らない）。
- 監査ログの主体は `user:{id}`。
- **先に済ませること**（`pending`）: 仮のパスワード（`must_change_password`）と、`--auth-require-mfa` で TOTP が未登録の利用者のパスワードのセッションは、
  自分の情報・ログアウト・パスワードの変更・TOTP の登録・自分のセッションの操作だけに使える（ほかは 403、`details.pending`）。毎回、利用者の状態から決める。
  OIDC のセッションには求めない（MFA は IdP の側の決まりに任せる）。
- 分散: 別のノードでの書き込みは、手元に適用されるまで数十 ms 遅れうる。ログインとコードの交換は、作ったセッションが手元に届くまで待ってから返す。
  知らないセッションの値が来たら、分散のときだけ 1.5 秒まで手元の状態を待つ（作ったばかりのセッションを別のノードで使ったとき）。

### パスワードのログイン

- `POST /auth/login` → 成功（`status: ok`）か、TOTP を登録した利用者には `status: mfa_required` と `mfa_token`。
  `mfa_token` は封じた値（5 分。テナント・利用者・その時点のパスワードのハッシュの SHA-256）で、状態には書かない（どのノードでも続きを受けられる）。
  `POST /auth/login/mfa` で TOTP のコードか回復コード。
- **使い回しの防止は `apply` で**: `CreateSession` に「確かめたパスワードのハッシュ」「受け付けた TOTP の区切り」「使った回復コードのハッシュ」を載せ、
  適用の時点で、パスワードが変わっていない・区切りが前回より後・回復コードが残っている、を確かめてから記録する。2 つのノードで同時に同じコードを使っても、
  通るのは先に適用された 1 つだけ。
- **利用者の列挙を防ぐ**: 失敗の応答は 1 種類（401、同じ本文）。利用者がいない・パスワードの無い利用者でも、起動後に 1 度だけ作った照合用のハッシュで同じだけ計算する。
- **総当たりを防ぐ**: 失敗を、送信元の IP アドレスごと（`--rate-limit-login`、既定 1 分に 10 回）と、アカウントごと（テナントと小文字の利用者名。
  利用者の有無にかかわらず数える。5 回までは待たせず、その後は 1 秒から倍々に、最長 15 分。1 時間失敗が無ければ数え直す。成功で消す）に数える。
  待たせている間は正しいパスワードでも 429。数えるのはノードごと（クラスタでは台数分まで試せる。既存の上限と同じ扱い）。
  アカウントごとの待ちは、攻撃者が他人のアカウントを最長 15 分ずつ止められるという面もある。待ちを長くしすぎないのはそのため。

### OIDC

- ノードが relying party になる。認可コードフロー、PKCE（S256）・`state`・`nonce` は必須。confidential client（シークレットはファイル）も public client もよい。
  クライアントの認証は、discovery が `client_secret_basic` に対応していれば（または何も書いていなければ）Basic、そうでなければ `client_secret_post`。
- **途中の値はクッキーに封じる**（複製しない）: `state`・`nonce`・PKCE の verifier・戻り先・redirect URI・ブラウザーの印（乱数）を封じて、
  `senca_oidc`（HttpOnly・SameSite=Lax・Path=/api/v1/auth・10 分、https なら Secure）に入れる。
  - 理由: 開始（`start`）は認証なしの要求なので、そのたびに Raft に書くと、誰でも合意ログを膨らませられる。封じる鍵はクラスタ共通なので、
    コールバックが別のノードに届いても開ける。期限と `state` の照合で、古いクッキーや別のフローの値は使えない。
  - SameSite=Lax: IdP からのコールバックはサイトをまたぐ最上位の GET なので、Strict では届かない。`response_mode=form_post` は使わない（Lax では届かない）。
- **一度きりのコードは複製する**: コールバックは利用者を決めた後、60 秒・1 回だけのコードを作り（`PutLoginCode`、状態にはハッシュだけ）、
  `/console/#/auth/complete?code=...` へリダイレクトする。コードは URL のフラグメントにあるのでサーバーには送られない。
  管理画面が `POST /auth/exchange` で替える（`RedeemLoginCode`: コードを消すのとセッションを作るのを 1 つのコマンドで）。1 回だけを守るには状態が要る。
  - コードは**ブラウザーの印と組**にする（コードの記録に印の SHA-256、交換のときにクッキーの印と比べる）。攻撃者が自分のコードを相手のブラウザーで
    交換させる（ログインの CSRF）ことを防ぐ。
- **取りに行く先**: 設定した発行者の `/.well-known/openid-configuration` と、そこに書かれた `jwks_uri`・`token_endpoint` だけ（トークンの中の URL へは行かない）。
  discovery の `issuer` は設定と同じでなければ使わない。発行者が https なら、書かれた宛先もすべて https でなければ使わない。
  通信は 10 秒・1 MiB まで。discovery と JWKS は 1 時間覚え、知らない `kid` なら JWKS を取り直す（5 秒に 1 回まで。ID トークンはこちらが
  トークンエンドポイントから取ったものだけなので、外から知らない kid を送り付けられることはない）。
- **外向きの接続の制限（仕様 9.4）との関係**: 発行者は管理者が設定した宛先なので、録画の保存先と同じく `--egress-allow` の検査を通さない
  （`httpc::request_trusted`）。社内の Keycloak（私設アドレス）に許可なしでつながるのはそのため。利用者が渡した URL には使わない。
- **ID トークンの検証**（OpenID Connect Core 3.1.3.7）は既存の `JwtVerifier` を使う。IdP の JWKS には暗号化用の鍵や対応しない鍵が混ざるので、
  それらを飛ばす読み方（`from_jwks_lenient`）を足した。確かめるもの: 署名（鍵が算法を決める）・`iss`（discovery の値）・`aud`（client_id を含む）・
  `exp`・`nbf`（60 秒のずれ）・`iat`（必須、未来でなく 10 分以内）・`nonce`（定数時間）・`azp`（あれば client_id、`aud` が複数なら必須）・`sub`、
  `max_age` を求めたなら `auth_time`。応答の `iss` パラメーター（RFC 9207）があれば発行者と比べる（IdP の取り違えを防ぐ）。
- **利用者の決め方**: (1) IdP と `sub` で結び付いた利用者 → (2) 同じメールアドレスの利用者（メールアドレスが確かめられたときだけ。結び付けて記録する）→
  (3) 自動で作る（`auto_provision`、パスワードの無い利用者）。どれにも当たらなければ断る（`no_account`）。
  - メールアドレスを信じるのは `email_verified: true` のときだけ（`require_email_verified`、既定 true）。Microsoft Entra ID は `email_verified` を出さず、
    `email` は利用者が変えられる場合がある（いわゆる nOAuth）。Entra ID では、結び付けを `sub` に任せ、役割の対応と自動作成で使うのを勧める。
  - テナントは固定（既定 `default`）かクレーム（`tenant_claim`）。クレームの値は 1〜64 文字の英数字と `._-` だけ。
  - 役割の対応（`role_mappings`）: クレーム（`groups`・`realm_access.roles` のような入れ子も）が値を含めば、その役割か権限。当たったものの和。
    当たらなければ `default_role`、それも無ければ断る（`no_role`）。`sync_roles`（既定 true）ならログインのたびに決め直す（最後の管理者の降格になるときは、今の役割のまま）。
    IdP の対応で `node:admin` も渡せる（設定は管理者のものなので、「`node:admin` は `node:admin` だけが渡せる」の規則の外）。
- 1 つの IdP はコマンドラインのオプション（`--oidc-*`）、複数は JSON（`--oidc-config`）。設定の誤り（形・クライアントシークレットのファイル）は起動しない。

### 最初の管理者と回復

- 最初の管理者は、今までどおりの最初の管理者トークン（`bootstrap-admin-token`）で `POST /users` を呼んで作る。`GET /auth/providers`（認証なし）の
  `setup_required` が、利用者が 1 人もいないことを示す（管理画面は「最初の管理者を作る」画面を出す）。専用の操作は作らない（トークンでできることを増やさない）。
- `senca-node reset-password --username NAME`: 動いているノードの管理 API を、管理者のトークンのファイル（既定は `{data-dir}/control/bootstrap-admin-token`、
  無ければ `recovery-admin-token`）で呼び、無効なら有効に戻し、MFA を外し、仮のパスワードを出す（次のログインで変更を求める）。`--create-admin` で作ることもできる。
  API を通すので、クラスタでも状態を直接書き換えない。
- `--recovery-admin-token`: 起動のときに管理者のトークン（`default` テナント、`tenant:admin`・`node:admin`、24 時間）をもう 1 つ作り、
  `control/recovery-admin-token`（0600、すでにあれば作らない）に書く。最初のトークンを消したり値をなくしたりしたときの回復に使う。
  データ置き場とノードの起動の引数を変えられる者は、もともと制御状態（鍵・トークンのハッシュ）をすべて読めるので、この方法で権限は増えない。

### 監査と SSE

- 監査ログ: `auth.login`（`outcome`: `success`・`failure`・`mfa_required`・`callback`、`method`: `password`・`password+totp`・`password+recovery_code`・`oidc:{id}`、
  `reason`、`ip`）、`auth.logout`、`auth.password.change`、`auth.mfa.enable`・`disable`・`recovery_codes`・`recovery_code_used`、`auth.session.revoke`、
  `user.create`・`update`（役割と権限、変わったか）・`delete`・`password.reset`・`mfa.reset`・`sessions.revoke`・`oidc.link`。
  パスワード・コード・トークン・秘密は書かない。知らない利用者名でのログインの失敗は `subject: anonymous` で、試した名前も書かない
  （利用者名の欄にパスワードを打ち間違えることがあるため）。
- SSE: `user.created`・`user.updated`（`data.change`: `profile`・`password`・`mfa`・`oidc_link`）・`user.deleted`。`tenant:admin` を持つ主体にだけ流す。
  セッションの出来事は流さない（量が多く、ほかの主体に見せるものでもない）。

## 選ばなかった案

- **OIDC の途中の値を複製する**: どのノードでも読めるが、認証なしの `start` のたびに合意ログへ書くことになる（上記）。
- **セッションを封じた値（ステートレス）にする**: 書き込みは減るが、ログアウト・パスワードの変更・無効化ですぐに失効させるには、結局失効の一覧を複製する必要がある。
- **最後に使った時刻をノードのメモリにだけ持つ**: クラスタでは要求がノードに散るので、ノードごとに違う判定になる。
- **コールバックで直接セッションを作り、値を URL に入れる**: 値がブラウザーの履歴やログに残る。
- **ログインの失敗の数をクラスタ全体で数える**: 失敗のたびに合意ログへ書くことになり、それ自体が攻撃の入口になる。

## 互換

- 制御状態の新しい項目は `#[serde(default)]`（前の版の写しを読める）。
- 新しいコマンドは前の版のノードでは読めない。クラスタでは、すべてのノードを新しい版にしてから利用者を作る（混在のまま利用者・ログインの操作をしない）。
